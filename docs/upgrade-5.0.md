# Upgrade Guide: 4.x → 5.0

Версия 5.0 — spec-conformance релиз. Постоянный набор тестов на соответствие [JSON-RPC 2.0 spec](https://www.jsonrpc.org/specification) нашёл семнадцать отклонений реального поведения от протокола; шестнадцать исправлены здесь. Почти все изменения BC-breaking, потому что исправление отклонения от спека по определению меняет наблюдаемое поведение.

## TL;DR

В отличие от 4.0, для 5.0 **нет единого YAML-конфига, который откатывает всё** — большая часть исправлений (сериализация через геттеры, точное сопоставление имён DTO, batch по форме контейнера, id/notification семантика, `-32000` вместо HTTP 403, обязательный `Content-Type`) это поведение протокола и обработки данных, а не тюнинг-параметры. Единственное исключение — `cors_strict`, который был конфигом, но **удалён без замены**: легаси comma-joined CORS-режима больше не существует ни при каком значении.

```bash
composer require otezvikentiy/json-rpc-api:^5.0
./vendor/bin/phpunit tests/   # прогнать вашу интеграцию заранее
```

После обновления зависимости — прогнать тесты, посмотреть на вывод, и пройтись по списку ниже пункт за пунктом. Каждое изменение — это баг предыдущей версии, исправленный по спеку; «откатить» в общем случае означает вернуться к нарушению протокола, поэтому миграция — это адаптация вызывающего кода, а не подкрутка конфига.

## BC-breaking changes

### 1. `Content-Type: application/json` обязателен

**4.x:** тело запроса парсилось как JSON независимо от заголовка `Content-Type`.
**5.0:** запросы с телом (POST/PUT/PATCH/DELETE) без `Content-Type: application/json` (с необязательным `; charset=...`) отклоняются с `-32600 Invalid Request`, даже если тело — валидный JSON. Form-encoded (`application/x-www-form-urlencoded`) и `multipart/form-data` отклоняются на этом же основании.

**Что сломается:**
- Клиенты, которые не выставляют `Content-Type` явно (некоторые HTTP-библиотеки по умолчанию используют `text/plain` или вообще ничего).
- Формы, отправляющие JSON-RPC вызовы как `application/x-www-form-urlencoded`.

**Что делать:**
- Убедитесь, что все клиенты явно ставят `Content-Type: application/json` на запросы с телом.
- Если вы намеренно принимали form-encoded — это больше не поддерживается: это закрывает CSRF-вектор (form-encoded — «simple request» по CORS-спеке, cross-origin форма могла вызывать ваши методы от имени залогиненного пользователя без preflight) и обход `max_payload_bytes`.

### 2. Скалярные параметры больше не приводятся

**4.x:** PHP слабая типизация приводила `"42"` к `int 42` при вызове сеттера.
**5.0:** `"42"` для поля `int` — `-32602 Invalid params`. Проверка идёт через `Symfony Validator` с `Assert\Type` без приведения, плюс любой `TypeError` из клиентского ввода на любом уровне (конструктор DTO, сеттер, аддер, вложенный DTO) конвертируется в `-32602` вместо `-32603`/необработанного исключения.

**Что сломается:**
- Клиенты, отправляющие числа строками (частый случай для form-data-подобных SDK или JS `URLSearchParams`).
- Тесты с моками, использующими `"1"`/`"0"` вместо `true`/`false` для boolean-полей.

**Что делать:**
- Отправляйте значения корректного JSON-типа: числа без кавычек, booleans как `true`/`false`, не строками.

### 3. Ответ сериализуется только через публичные геттеры

**4.x:** сериализация ответа читала свойства класса напрямую через `ReflectionProperty::getValue()`.
**5.0:** в JSON попадает только то, для чего есть публичный геттер (`getFoo()`, `isFoo()`, `foo()`). Свойство без геттера — не сериализуется, даже если оно публичное.

**Что сломается:**
- Response-классы с публичными свойствами без геттеров — эти поля молча исчезнут из ответа.
- Response-классы, наследующие поля от родительского класса без собственного геттера в потомке, если раньше вы полагались на прямое чтение через Reflection родительского приватного свойства (маловероятно, но возможно — раньше это работало случайно, а не по контракту).

**Что делать:**
- Добавьте геттер для каждого свойства, которое должно попасть в ответ.
- Проверьте существующие Response-DTO на «случайно видимые» приватные поля без геттера — теперь это тоже безопаснее: то, что раньше утекало через голое Reflection (например, поле, которое разработчик не думал экспонировать), больше не попадёт в ответ вообще, если у него нет геттера. Если поле раньше **намеренно** отдавалось без явного геттера — добавьте геттер.

### 4. Циклический граф объектов в ответе — `-32603`, а не падение воркера

**4.x:** двунаправленная связь (`Order` → `User` → его `Order`ы) приводила к бесконечной рекурсии и segfault воркера — без ответа, без лога.
**5.0:** обнаружение цикла (`SplObjectStorage` visited-set) бросает `JRPCException` с `-32603 Internal error`, клиент получает корректный JSON-RPC ответ, `ErrorSanitizer` логирует.

**Что сломается:** ничего наблюдаемого клиентом раньше не работало (сервер падал) — теперь работает предсказуемо.
**Что делать:** если ваш DTO-граф действительно циклический по бизнес-смыслу — разорвите цикл на уровне DTO (например, не включайте обратную ссылку в Response-объект).

### 5. `DateTimeInterface` сериализуется в ISO 8601

**4.x:** `BaseResponse` не имел спецобработки дат — `DateTime`/`DateTimeImmutable` разваливались на пустой массив внутренних свойств вместо строки.
**5.0:** любой `DateTimeInterface` (включая `DateTimeImmutable`) форматируется в ISO 8601 (`DATE_ATOM`) и в ответе, и в `JsonRpcRequest::toArray()`.

**Что сломается:** клиенты, которые уже как-то мирились с пустым `{}` вместо даты в ответе — маловероятно, но если такой код существует, он перестанет получать `{}`.
**Что делать:** ничего — это чистое исправление бага. Если раньше вы вручную форматировали дату геттером (`getCreatedAtFormatted(): string`) в обход бага — можно (не обязательно) упростить до `getCreatedAt(): DateTimeImmutable`.

### 6. Методы DTO привязываются к свойствам по точному имени

**4.x:** геттер резолвился через `str_contains()` — `getUserId()` мог случайно удовлетворить и свойство `userId`, и свойство `id`. Сеттеры регистрировались по имени **параметра**, а не свойства.
**5.0:** строгое совпадение по имени свойства. Аддеры коллекций резолвятся через `Symfony\Component\String\Inflector\EnglishInflector` (`children` → `addChild`), а не отбрасыванием последней буквы (`children` → `childre`, молча ничего не добавляя).

**Что сломается:**
- DTO с парами свойств, где имя одного — подстрока другого (`id`/`userId`, `token`/`refreshToken`, `name`/`fullName`): раньше валидатор мог незаметно проверять не то поле.
- DTO с неправильными множественными числами в названии коллекции (`children`, `people`, `data`), у которых аддер раньше молча не находился и коллекция оставалась пустой без ошибки. Теперь либо резолвится верно, либо — если имени всё равно нет соответствия — контейнер не скомпилируется (`Property %s has no accessible getter`), а не тихо промолчит в рантайме.

**Что делать:** проверьте DTO с похожими именами свойств и с нестандартными множественными числами коллекций. Если сборка контейнера падает на compile-time ошибке про отсутствующий геттер — это, скорее всего, вскрывшийся баг, который раньше маскировался неверным биндингом.

### 7. `allow_extra_fields` применяется на любой глубине одинаково

**4.x:** флаг проверялся один раз на верхнем уровне; рекурсивная гидратация вложенных DTO отклоняла лишние поля безусловно, даже при `allow_extra_fields: true`.
**5.0:** один и тот же флаг (`allow_extra_fields` глобально + `allowExtraFields` per-method) применяется на каждом уровне рекурсии одинаково.

**Что сломается:** если вы полагались на то, что `allow_extra_fields: true` разрешает лишние поля только на верхнем уровне, а вложенные DTO их всё равно отклоняют (маловероятный, но возможный частный случай) — теперь и вложенные DTO тоже разрешат.
**Что делать:** обычно ничего — это выравнивание поведения под ожидаемое.

### 8. Batch определяется по форме контейнера

**4.x:** массив признавался batch'ем, только если первый элемент был валидным объектом-запросом (`jsonrpc` + `method`). Невалидный первый элемент откатывал всю обработку в single-request режим, и валидные вызовы дальше в массиве **терялись без единого сигнала об ошибке**.
**5.0:** любой непустой JSON-массив-список (`array_is_list()`) — batch, независимо от валидности элементов. `[{"foo":"boo"}, {валидный запрос}]` теперь возвращает массив с ошибкой для первого и результатом для второго.

**Что сломается:** клиенты, которые полагались (пусть и случайно) на старое поведение отбрасывания всего batch'а при невалидном первом элементе.
**Что делать:** ничего специального — новое поведение строго полезнее. Проверьте свои интеграционные тесты, если они жёстко фиксировали старую отбраковку.

### 9. `{"id": null}` — полноценный запрос, Notification не получает ответа никогда

**4.x:** `isset($data['id'])` не различал «поля `id` нет» и «`id` есть и равно `null`» — оба случая обрабатывались как Notification. Одиночный Notification с непустым ответом от `call()` возвращал `"{}"` вместо пустого тела — сервер сам себе противоречил, `"{}"` это ответ, а Notification ответа получать не должен.
**5.0:** `BaseRequest` трекает наличие ключа `id` отдельно от значения. `{"id": null}` — полноценный запрос, всегда получает ответ (`"id": null` в ответе). Отсутствие `id` — Notification, который никогда не получает ответа, включая случай, когда `call()` бросил исключение. Единственное исключение — конверт запроса настолько повреждён, что нельзя достоверно установить, был ли это Notification: такой случай всё ещё получает диагностику.

**Что сломается:**
- Клиенты, отправлявшие `{"id": null}` и ожидавшие тишины (нестандартное использование, но было возможно).
- Клиенты, отправлявшие Notification и получавшие `"{}"` вместо пустого тела.

**Что делать:** если вам действительно нужен Notification — не передавайте `id` вообще, не передавайте `"id": null`.

### 10. `params: null` отклоняется

**4.x:** `isset($data['params'])` пропускал явный `"params": null`, трактуя его как «параметров нет».
**5.0:** `array_key_exists('params', $data) && !is_array($data['params'])` — явный `null` в `params` теперь `-32600 Invalid Request`, как того требует раздел 4 спека (params, если присутствует, должен быть структурированным значением).

**Что сломается:** клиенты, явно отправляющие `"params": null` вместо того, чтобы просто не передавать `params`.
**Что делать:** не передавайте `params`, если параметров нет — не передавайте `null`.

### 11. Отказ по ролям — `-32000` в JSON-RPC error-объекте, а не HTTP 403

**4.x:** `RequestHandler` возвращал `JsonResponse` со строкой `"Access not allowed"` и HTTP 403 — не JSON-RPC объект. Внутри batch это ломало структуру: строка сплайсилась в массив ответов как есть, `id` терялся, а статус 403 пропадал, потому что весь batch-ответ пересобирался с кодом 200.
**5.0:** отказ бросает `JRPCException` с кодом `-32000`, проходит обычный путь построения ошибки — корректный объект с правильным `id`, HTTP 200, работает и одиночно, и внутри batch.

**Что сломается:** мониторинг/алертинг, считающий долю HTTP 403 как прокси для отказов по ролям.
**Что делать:** читайте `error.code === -32000` вместо HTTP-статуса. См. [security/roles.md](./security/roles.md).

### 12. Коды ошибок нормализуются в допустимый диапазон

**4.x:** произвольный `Throwable` с кодом `0` (или другим вне стандартных значений и `-32000..-32099`) уходил клиенту как есть при `expose_internal_errors: true`.
**5.0:** код вне допустимых диапазонов принудительно заменяется на `-32603`.

**Что сломается:** код, парсящий `error.code` не-JRPCException исключений при `expose_internal_errors: true` и ожидающий произвольные значения (нестандартный сценарий).
**Что делать:** обычно ничего — `expose_internal_errors: true` и так рекомендуется только для dev.

### 13. Имена схем OpenAPI изменились

**4.x:** схема называлась по короткому имени класса. Проекты, где Response/Request классы лежат в `RPC/V<n>/<Method>/Response.php` (частая структура — см. [структуру файлов](./examples/base.md#структура-файлов)), получали десятки классов с коротким именем `Response`, которые тихо затирали друг друга в одном ключе `components/schemas`.
**5.0:** схема ответа — `{methodName}Response`, схема параметров — `{methodName}Request`, вложенные DTO — по полному имени класса (`\` → `.`).

**Что сломается:** инструменты, сгенерировавшие клиентский код по старым именам схем (`Response`, `Request`, `Product`) — пересоздайте клиент по новому `openapi.yaml`.
**Что делать:** перегенерируйте Swagger (`bin/console ov:swagger:generate`) и любой клиентский код, зависящий от точных имён схем.

### 14. `cors_strict` удалён

**4.x:** `cors_strict: true` (дефолт) — строгое поведение; `false` — легаси comma-joined заголовок.
**5.0:** ключ **удалён без замены**. Поведение всегда как было при `cors_strict: true`. Оставшийся в конфиге ключ `cors_strict` — ошибка компиляции контейнера (`InvalidConfigurationException`), а не проигнорированное значение.

**Что сломается:** конфиги с явным `cors_strict: true` или `cors_strict: false` — оба варианта роняют приложение при старте.
**Что делать:** удалите строку `cors_strict` из `config/packages/ov_json_rpc_api.yaml`. Если вы полагались на `cors_strict: false` (легаси comma-joined режим) — такого поведения больше нет ни при каком конфиге; перечислите нужные origin'ы явно в `access_control_allow_origin_list`.

### 15. CORS preflight (`OPTIONS`) теперь обрабатывается бандлом

Не BC-breaking для существующих клиентов, но меняет форму ответа на `OPTIONS /api/v{version}` — раньше это был 404/405 (если только вы не настраивали preflight отдельно на nginx/CORS-бандле), теперь `204 No Content` с полным набором CORS-заголовков. Если вы настраивали preflight отдельно — это, скорее всего, стало избыточным; см. [cors.md](./cors.md).

Новый конфиг `cors_allowed_headers` (default `['Content-Type']`) — расширьте, если фронтенд шлёт кастомные заголовки (например, `X-AUTH-TOKEN`).

### 16. Границы зависимостей в манифесте

**4.x:** `composer.json` объявлял зависимости без верхней границы (`>=X`), включая `php: ">=8.2"`.
**5.0:** `symfony/*: ^6.4 || ^7.0`, `php: 8.2.* || 8.3.* || 8.4.*`. `doctrine/annotations` убран из require.

**Что сломается:** `composer require` больше не сможет молча подтянуть непроверенный Symfony 8 или PHP 9. Если вы уже используете что-то из этого — обновление до 5.0 потребует сначала выровнять версии инфраструктуры.
**Что делать:** обычно ничего — верхние границы лишь фиксируют то, на чём бандл реально тестируется. Если вы явно полагались на `doctrine/annotations`, транзитивно подтянутый бандлом — объявите зависимость в своём проекте напрямую.

### 17. Контейнер не алиасится в приложение, RPC-методы не публичные

**4.x:** `config/services.yaml` бандла содержал алиас `Symfony\Component\DependencyInjection\Container: '@service_container'`, поэтому любой сервис приложения мог получить контейнер целиком, просто типизировав им параметр конструктора. Из-за этого же каждый RPC-метод регистрировался публичным сервисом.
**5.0:** алиас удалён, RPC-методы приватны. `RequestHandler` получает `ServiceLocator`, собранный по тегу `ov.rpc.method`.

**Что сломается:** сервис вашего приложения с конструктором вида `__construct(private Container $container)` перестанет собираться — `Cannot autowire service ...: argument $container of type Symfony\Component\DependencyInjection\Container`. Достучаться до RPC-метода через боевой контейнер (`$container->get(MyMethod::class)`) больше нельзя — `ServiceNotFoundException: ... has been removed or inlined`.
**Что делать:** **замены алиасу нет намеренно** — инжектируйте нужные сервисы напрямую вместо контейнера целиком. В тестах доступ к приватным сервисам сохраняется: `KernelTestCase` + `self::getContainer()->get(MyMethod::class)` работает как раньше, потому что тестовый контейнер отдаёт приватные сервисы.

Заодно тридцать классов помечены `@internal` — весь `src/DependencyInjection/`, весь `src/Swagger/`, а также конвейер обработки запроса: `ApiController`, `RequestHandler`, `RequestRawDataHandler`, `ResponseService`, `HeadersPreparer`, `ErrorSanitizer`, `BatchStrategyFactory`, обе batch-стратегии и `HandleBatchInterface`. В боевом коде приложение ни один из них не конструирует — это делает контейнер; метка нужна, чтобы дорабатывать их внутри 5.x, не дожидаясь следующего мажора. Исключение — тесты: харнесс из [testing.md](./testing.md) собирает часть стека руками и **описывает `MethodSpec` вручную**, а `MethodSpec` с его метаданными тоже помечены `@internal`. `MethodSpecCollection::getMethodNames()` удалён: он возвращал номера версий API, а не имена методов, и единственным его вызывающим был собственный тест.

Что метку **не** получило и остаётся публичным контрактом: `ApiMethodInterface`, `PreProcessorInterface`, `PostProcessorInterface`, `PlainResponseInterface`, `OvResponseInterface`, `PartialRequestInterface`, `JsonRpcRequest`, `BaseRequest`, `BaseResponse`, `JRPCException`, атрибут `#[JsonRPCAPI]`, логирующие интерфейсы и ключи конфигурации.

Практическое следствие: если ваш тестовый харнесс собирает `RequestHandler`/`ResponseService`/`HeadersPreparer` руками или описывает `MethodSpec` вручную (как показано в [testing.md](./testing.md)), он опирается на внутренности осознанно, и их сигнатуры могут поменяться в минорном релизе 5.x. Это допустимый размен — быстрый тест без поднятия ядра, — но именно размен, а не бесплатная скорость. Интеграционный тест через `KernelTestCase` от этого свободен: там стек и `MethodSpec` собирает контейнер.

### 18. Маскирование логов включено по умолчанию

**4.x:** `logging.masking.key_patterns` — пустой список, `logging.max_body_length` — `0` (без обрезки). Одной строки `logging.enabled: true` хватало, чтобы в лог пошли полные тела запросов и ответов, пароли включительно.
**5.0:** `key_patterns` — двадцать девять паттернов по умолчанию (`password`, `token`, `secret`, `authorization`, `jwt`, ключи сертификатов и прочее), `max_body_length` — `8192`.

**Что сломается:** если логирование у вас уже включено, на месте значений появятся `***`, а длинные тела будут обрезаны. Дашборды и алерты, разбирающие поля из тела лога, могут перестать находить данные. Битое регулярное выражение в `key_patterns` теперь роняет компиляцию контейнера — раньше оно молча отключало маскировку для этого паттерна и сообщало об этом одним warning'ом за жизнь процесса.
**Что делать:** если поле маскируется зря — сузьте `key_patterns` под свой список; если тела нужны длиннее — поднимите `max_body_length`. Возвращать `key_patterns: []` не стоит: это ровно та конфигурация, из-за которой пароли попадали в лог. Полная таблица параметров — [logging.md](./logging.md).

## Что НЕ ломается

- `#[JsonRPCAPI]` атрибут — все параметры и семантика версионирования не изменились.
- `ApiMethodInterface` и сигнатура `call()`.
- `JRPCException` — все коды и API, конструктор, `additionalInfo`.
- `PartialRequestInterface`, `PartialUpdateRequest`, `TracksProvidedFieldsTrait`, `wasProvided()` семантика.
- Pre/Post-процессоры — сигнатуры и порядок вызова (`finally`-семантика PostProcessor) не изменились.
- `strict_notifications`, `expose_internal_errors`, `allow_extra_fields`, `max_payload_bytes`, `max_batch_size`, `max_json_depth`, `max_dto_depth`, `max_array_param_size` — те же ключи, те же дефолты, что и в 4.x. Исключение — `logging.max_body_length`, у него дефолт изменился, см. п. 18.
- Формат ошибки `{jsonrpc, error: {code, message}, id}` не изменился.
- Точки расширения: `ApiMethodInterface`, `PreProcessorInterface`, `PostProcessorInterface`, `PlainResponseInterface`, `PartialRequestInterface`, `JsonRpcRequest`, `BaseResponse`, `JRPCException` и логирующие интерфейсы метку `@internal` не получили и остаются частью публичного контракта.

> **Оговорка к последнему пункту.** «Остаются публичным контрактом» — про то, что классы не помечены внутренними, а не про то, что их поведение не изменилось. У двух из них изменилось: `BaseResponse` сериализует только через публичные геттеры (п. 3), а `JsonRpcRequest::toArray()` теперь делает то же самое и может выбрасывать `JRPCException` на циклическом графе — см. раздел «Изменено (BC-breaking)» в [CHANGELOG.md](../CHANGELOG.md) и [json_rpc_request.md](./json_rpc_request.md). Остальные перечисленные не изменились ни в сигнатурах, ни в поведении.

## Чек-лист апгрейда

1. `composer require otezvikentiy/json-rpc-api:^5.0`.
2. Удалите `cors_strict` из конфига, если он там есть — иначе приложение не соберёт контейнер.
3. Прогоните тесты. Большинство падений — про строгую типизацию, геттер-only сериализацию или изменившиеся имена OpenAPI-схем.
4. Пройдитесь по клиентам: везде ли выставлен `Content-Type: application/json` на запросах с телом; нигде ли параметры не отправляются числом-строкой.
5. Проверьте Response-DTO на свойства без геттеров, которые раньше молча сериализовались через Reflection.
6. Перегенерируйте Swagger/OpenAPI-клиенты (имена схем изменились).
7. Если мониторите отказы по ролям через HTTP-статус — переключитесь на `error.code === -32000`.
8. Проверьте DTO с похожими именами свойств (`id`/`userId`) и нестандартными множественными числами коллекций (`children`, `people`) — раньше это могло маскировать баг.
9. Поищите в своём коде конструкторы, типизированные как `Container`, и обращения к RPC-методам через боевой контейнер — и то и другое больше не соберётся (п. 17).
10. Если логирование включено — сверьте `key_patterns` и `max_body_length` со своими ожиданиями: маскирование теперь работает из коробки (п. 18).

## Откат

В отличие от 4.0, «всё как раньше одним конфигом» для 5.0 не существует — большинство исправлений это поведение протокола, а не переключаемые настройки. Если критично нужно временно откатиться — зафиксируйте зависимость на последней `4.x`-версии (`composer require otezvikentiy/json-rpc-api:^4.2`) и мигрируйте по этому гайду отдельным шагом, а не через конфиг.
